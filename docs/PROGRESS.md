# 职业与 JP：1.0

## 角色与操作边界

独立页面提供觉醒者、主随从、双方三个范围，默认觉醒者。普通职业选择双方时设置相同目标值；任一目标缺席或保护数据不可用便取消整个操作。已核验的 Job01～06 可用于随从，Job07～10 只用于觉醒者；未知职业只读。选择双方并操作专属职业时预览只列觉醒者；JP 始终按角色选择，不随职业过滤。

资格来自 `isJobQualified(JobEnum)`。解锁仅调用 `setJobQualified`，保留 ChangedJobBits、ViewedNewJobBits、JP、经验、全部技能与装备；不会冒充首次转职已完成。锁定保留进度，只清指定资格位。正在使用的职业必须先转职；Job01～04 为基本可用职业，不强制锁定。高级职业位图候选为 ID 位或 ID-1 位，须与可访问角色的原生资格逐项比较且唯一；随从专属禁用职业不作为随从的推断证据。未知/有歧义时仅锁定按钮不可用。

等级选项采用角色原生 `getMaxJobRank` 的结果，双方范围取其交集。当前实现对异常大于 128 的返回值拒绝建表并要求诊断，防止错误接口导致无限分配；128 是损坏数据防护，不是游戏最高职业等级。通过 `setJobExpWithJobRank(JobEnum, UInt32)` 设置，`calcJobRank` 与 `getJobExp(JobEnum)` 验证。不使用战斗经验分发接口；不会加 JP、人物经验或技能。同级操作不写，保存等级内进度；改变等级由游戏接口选择该等级对应的累计经验。

JP 是每个角色的 ConsumableExp 总余额，不是按职业分别存储。`set_ConsumableExpProp(Int32)` 接受 0～2147483647 的绝对余额；原生 getter 与字段共同回读。没有增加/扣减或连续覆盖模式。游戏拒绝、钳制或回读不一致属于失败，恢复原始余额。

## 分层与共享流程

控制器用 skills/progress 注册表共用规格、预检、预览确认、写盘回读、再次定位、执行、日志和持久化修改锁。职业模块实现 specification/prepare/backup/execute；适配器负责明确签名的原生读写和恢复。UI 只接收导出的普通数据并提交请求；跨帧不缓存角色、上下文或装箱对象。隐藏职业页复用界面快照，不额外反复扫描成长/武器护甲保护；实际操作每次重新完整核验。

JP、等级、资格接口分别预检；单项 getter 失败不遮蔽其他项。恢复方法和保护结构属于所有职业写入的共同前提。读取缓存保留类型字段描述，不保留游戏对象。角色/场景变化清空状态；请求、确认和保存快照后的三次完整指纹须一致。

进度请求包含 kind、target、job_id（JP 无此项）、value（等级/JP）、roles、目录戳；预览保存 domain=progress、字段代码、角色与前后值。schema 5 日志附操作类别、实际目标、完整原始经验、资格映射及保护数据。修改角色、职业、页面、语言、输入等级或 JP 会取消旧预览。

## 校验与精确恢复

保存并保护所有职业的原始经验/资格/首次转职标记、全部主动和基础技能、全部技能槽、人物等级/经验/成长、所有被动学习与装备记录，以及保存的职业武器/护甲配置。只有请求指定的资格、该职业经验或 JP 允许变化；全部其他字段/原生 getter 必须保持一致。正常修改不清空装备或学习技能。

职业经验数组为 System.Int32[]。每次核对长度、当前 get_JobIndex 与指定职业 getJobExp 和保存数组，正常等级写入完全走游戏原生接口。最终执行时 pin 原始上下文、数组、学习记录和 GetValue 返回的独立 Int32 boxes；回滚逐项恢复原始经验，而非用等级 setter 丢失等级内进度。

恢复赋值通过 REFramework SystemArray 的受检下标/托管装箱机制。已保存与本机对应的 SystemArray.cpp/.hpp：主路径调用 System.Array.SetValue(Object, Int32)，备用路径调用受类型检查的数组 Set(Int32, Int32)。实际数组至少有一条准确签名才允许职业写入；不创建假对象、不猜装箱数据偏移、不使用裸内存接口。恢复后同时校验原始数组值与原生职业 getter。

任何写入/核验失败倒序恢复全部目标职业数据，并恢复原技能与技能槽，再统一核验。人物成长、被动及武器护甲属于保护边界；若原生接口意外修改这些系统且完整恢复无法证明成功，停用全部写入、保存 writer-lock、导出诊断，要求完整存档恢复。不会将部分恢复显示为成功。

## 验证状态

已有第三次游戏诊断确认职业 rank/JP/资格 setter/getter 及人物/被动上下文访问方法的准确签名；当前 RSZ 核对新保护字段。新增保护集合、数组恢复与资格位图的实际行为仍需 schema 5 游戏诊断与人工验收。字体接口与字号参数已核对官方文档和本机 REFramework 源码。所有自动检查仅语法编译、AST、接口/资料引用、编码、哈希和包结构；没有执行 Mod 仿真或自动化游戏测试。

## 1.0：校验修正与批量解锁

0.4.0 的 guard() 虽然删除了 protected_progress.job，仍保留 access.guards 返回的 fingerprint，其中包含 JP、资格位及职业经验。任意正确的职业修改均使此旧指纹变化，造成“额外变化”的误判与回滚。1.0 同时移除这个衍生指纹；基础技能开关 / 记录、完整学习与装备、人物 / 成长 / 被动 / 武器护甲的原始值仍逐项比较。职业字段与经验由独立白名单核验。保护失败日志现在记录具体字段路径，便于定位真实差异。

vocation_unlock_all 从同一职业目录构造角色 / 职业项，按既有适用规则跳过主随从专属禁用职业及未知职业。每个角色只采集一次完整快照，全部项在任何写入之前校验；仅对未解锁项调用 setJobQualified，已解锁项没有写入。最终资格位差异须与目标掩码一致；无法核实映射时仍必须满足新增位数、保留原位和逐职业原生查询的整体校验。经验、等级、首次转职、已读标记、JP、技能与装备均须保持一致。任何目标失败则恢复全部角色原始数据。

UI 当前状态固定显示双方当前职业 / 等级 / JP，编辑区另显示所选职业在双方的状态；角色选择仅决定请求范围，不隐藏比较信息。确认与放弃使用局部颜色栈并异常清理；顶部和确认区同时显示待确认提示，确认 / 放弃 / 修改选择后取消旧预览。配色枚举来自已安装 REFramework 对应 Dear ImGui 1.92.0 头文件，详见 references/manifest.json。
